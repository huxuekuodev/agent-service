# 会话持久化与历史回放方案

> 现状：`AgentService.create_session()` 只生成随机 `session_id`（= LangGraph `thread_id`）不落库；
> `list_sessions()` 固定返回 `[]`；`delete_session()` 是 TODO；前端无 `localStorage`。
> 因此刷新/重开浏览器后：列表丢失、历史对话无法回看。
> 但 **对话内容其实已经在服务端**——`database.backend=postgres` 时，LangGraph checkpointer
> 按 `thread_id` 持久化了完整状态（含 messages / plan_tasks），并提供 `alist` / `aget_tuple` /
> `adelete_thread` 能力。

## 1. 目标

1. 会话**服务端持久化**：创建即入库，列表/历史可查、可重命名、可删除；
2. 浏览器**保持当前会话**（刷新/重开仍在原会话，消息完整回显）；
3. 历史消息**面向用户口径**渲染（过滤内部消息：tool dump、结构化输出、ToolMessage）；
4. 为后续能力留位：多端同步、分页/搜索、`ui_messages` 事件回放（澄清卡片/步骤进度）、interrupt/resume。

## 2. 数据来源：三种方案

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 只读 checkpointer | `graph.aget_state({"configurable":{"thread_id": id}})` 取 `messages`，过滤成 UI 消息 | 零冗余、无需新表、天然与 agent 状态一致 | 每次读需反序列化整份 state；分页/搜索只能应用层做；与 LangGraph 表结构耦合 |
| B. 双写消息表 | 新增 `sessions` + `messages`，在每个对话轮次写入用户消息与最终答复 | 列表/历史/搜索/分页自由，标题与预览易做，与 LangGraph 解耦 | 需保证一致性（以 checkpointer 为真相，消息表可重建） |
| **C. 混合（推荐）** | `sessions` 表存元数据 + `messages` 存用户口径消息；**checkpointer 仍是 agent 状态唯一真相**，消息表可由 `alist` 重建 | 兼顾查询能力与真相单一 | 需一次"重建/校对"任务（可做成脚本或启动期校验） |

**结论：采用 C。** 消息表只读落地"用户口径"（HumanMessage + 最终 AIMessage），内部消息不进表；
需要完整调试视图时走 A（`GET /sessions/{id}/state`）。

## 3. 数据模型（PostgreSQL）

**以 `deploy/sql/business_schema.sql` 为准**（幂等，可直接执行），本节只列与"会话/历史回放"直接相关的部分：

| 表 | 关键字段 | 说明 |
|----|---------|------|
| `users` / `user_identities` / `user_tokens` | `password_hash` / `jti, token_hash, expires_at, revoked_at` | 账号密码 + JWT（refresh 可撤销、可旋转） |
| `sessions` | `id UUID`、`user_id`、`title`、`status`、`model_role`、`checkpoint_thread_id`、`message_count`、`last_message_at`、`last_preview`、`deleted_at` | 会话元数据；`checkpoint_thread_id` 默认 = `id::text` |
| `messages` | `id BIGSERIAL`、`session_id`、`user_id`、`seq`、`role`、`kind`、`content`、`payload`、`token_*`、`created_at`、`deleted_at`；**PK `(id, created_at)`，按月 RANGE 分区** | 消息长期真相；分区表唯一索引必须含 `created_at` |
| `message_idempotency` | PK `(session_id, client_msg_id)` → `message_id, message_created_at` | 分区表无法对 `client_msg_id` 建全局唯一索引，故独立小表承载前端重发幂等 |
| `session_events` | `session_id, seq, type, phase, payload, created_at` | 过程事件（30 天 TTL，`cleanup_session_events()`） |

写入统一走 `append_message(...)` 存储过程：`ensure_message_partition_for(now())` 补分区 → 幂等校验 →
`UPDATE sessions` 行锁分配 `seq` 并刷新 `message_count / last_message_at / last_preview`（避免 `MAX(seq)` 竞态）。
`app/session/store.py` 复用 `app/monitor/store.py` 的 PG 连接池模式（连接业务库 `BUSINESS_DATABASE_URL`）。

## 4. 接口设计（沿用 `{data,msg,status}` 信封）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/sessions` | 创建会话（写 `sessions` 行，返回 `session_id/thread_id/title/created_at`） |
| GET | `/sessions?limit=20&cursor=&q=` | 列表（按 `updated_at desc`，支持游标分页与标题搜索） |
| GET | `/sessions/{id}` | 会话详情（元数据 + 是否 `completed`） |
| PATCH | `/sessions/{id}` | 重命名 / 归档（`title`、`meta`） |
| DELETE | `/sessions/{id}?hard=false` | 软删（默认）或硬删（连 `adelete_thread` 一并清理） |
| GET | `/sessions/{id}/messages?limit=50&before_seq=` | 历史消息（用户口径，倒序分页倒排后正序返回） |
| GET | `/sessions/{id}/state` | 调试视图：原始 `messages` / `plan_tasks`（A 方案，限管理员） |
| POST | `/sessions/{id}/chat` | 既有 SSE（不变）；首轮自动写标题与 preview |
| POST | `/sessions/{id}/resume` | 预留：interrupt 人工介入恢复 |

**写入时机**：`chat` 流结束（含失败）时，用同一事务写：`user` 消息 + `assistant` 最终答复（澄清时写
`kind=clarify`），并更新 `sessions.message_count / last_preview / updated_at`；标题 = 首条用户消息前 20 字。

**用户身份（已定：账号密码 + JWT）**：`Authorization: Bearer <access_token>`，后端依赖注入解析出 `user_id`
（缺失/失效 401，**不落匿名会话**）。access 短时效无状态校验，refresh 落 `user_tokens` 可撤销并旋转；
新增接口：`POST /auth/register`、`POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`GET /auth/me`。
这同时解决"token 统计目前拿 session_id 当用户"的问题（改用 user_id）。

## 5. 前端改造（`web/src/`）

1. **持久化当前会话**：`localStorage.setItem('dsh.currentSessionId', id)`；启动时读取，优先恢复；
2. **列表加载**：`onMounted` → `GET /sessions`（替换现在"远端空列表 + 本地兜底"的写法）；
3. **历史回显**：选中会话 → `GET /sessions/{id}/messages` → 渲染气泡（`role` 直接映射 user/assistant）；
4. **离线兜底**：`localStorage` 缓存最近列表与当前会话消息（首屏秒开），远端返回后覆盖；
5. **标题**：首轮发送后本地更新 + 服务端已写库，二者一致；
6. **删除/重命名**：调用 PATCH/DELETE，界面即时更新；
7. （后续）事件回放：用 `ui_messages` 渲染澄清卡片、计划清单、步骤进度（见 `docs/消息流转与展示方案.md`）。

## 6. 迁移与兼容

- **老会话导入**：`checkpointer.alist({"configurable": {"thread_id": ...}})` 枚举全部 thread →
  读取 `aget_tuple(...).checkpoint["channel_values"]["messages"]` → 过滤用户口径 → 写入
  `sessions/messages`（一次性脚本 `scripts/backfill_sessions.py`，幂等，按 `session_id` upsert）；
- **一致性校验**：写库失败不阻塞对话（`try/except + 日志`），并提供"以 checkpointer 重建指定会话"的修复入口；
- **删除语义**：默认软删（保留打点/审计）；不提供物理删除接口，否则按 `checkpoint_thread_id` 调 `adelete_thread` 一并清理 checkpoint。

## 7. 分阶段实施

**P0（最小可用，先解决"刷新丢会话"）**
1. `app/session/store.py`（PG + memory 双实现，复用 monitor 的连接池模式与建表方式）；
2. `AgentService` 接入：`create_session/list_sessions/get_messages/rename/delete`（替换现有空实现）；
3. 路由：`GET /sessions`、`GET /sessions/{id}/messages`、`PATCH`、`DELETE`；
4. `chat` 结束后落库（user + 最终答复 + 更新元数据/标题）；
5. 前端：localStorage 当前会话 + 列表加载 + 历史渲染。

**P1**：认证（账号密码 + JWT：注册/登录/刷新/登出 + `user_id` 隔离）、游标分页、标题搜索、重命名、软删；token 统计按 `user_id`；老会话 backfill。

**P2**：`ui_messages` 事件回放（澄清/计划/步骤卡片）、interrupt/resume、多端实时同步（同一 user_id 多标签）。

## 8. 决策结论（已确认）

| # | 决策点 | 结论 |
|---|--------|------|
| D1 | 历史来源 | **消息表为长期真相**：checkpoint 可能被压缩/清理，消息记录必须长期保留 → 采用「业务库表结构」而非只读 checkpoint |
| D2 | 存储 | **独立业务库（与 checkpoint 库分离）**，包含 用户表 / 会话表 / 消息表（+ 扩展表），DDL 见 `deploy/sql/business_schema.sql` |
| D3 | 用户身份 | **真实用户**：以 `users` 表为准，会话归属 `user_id`（不再用 session_id 冒充用户） |
| D4 | 删除语义 | **逻辑删除（deleted_at）**，不物理删除；会话绑定 `checkpoint_thread_id`，后期定时任务清理陈旧会话时一并删除 checkpoint |
| D5 | 认证方式 | **账号密码 + JWT**：`users`（Argon2id/bcrypt 哈希）+ `user_identities` + `user_tokens`（refresh 哈希落库、可撤销、登录时旋转） |
| D6 | monitor 三表 | **迁入业务库**（`monitor_components / monitor_field_meanings / user_token_usage`），监控平台与业务数据同库同连接池 |
| D7 | messages 分区 | **按月 RANGE 分区**（`messages_YYYYMM`）：`append_message` 内自动补建分区 + 建议定时 `ensure_message_partitions(1, 3)` 双保险 |
| D8 | session_events 保留期 | **30 天**：`cleanup_session_events(30)` 函数已提供；**后端定时任务暂不实现**（本轮不做该业务） |

> 表结构、字段语义、索引策略、运维 SQL 与接口映射详见 **`docs/业务库表结构设计.md`**。
