# 业务库表结构设计（用户/会话/消息）

> 决策基线（已确认，不再变更）：
> 1. **业务库与 LangGraph checkpoint 库分离**；`messages` 是长期真相（checkpoint 可被压缩/清理，消息不丢）；
> 2. 认证方式：**真实用户 + 账号密码 + JWT**（access + refresh，refresh 落库可撤销）；
> 3. `monitor_components / monitor_field_meanings / user_token_usage` **迁入业务库**；
> 4. `messages` **按月 RANGE 分区**；`session_events` **保留 30 天**（清理函数已提供，后端定时任务暂不实现）；
> 5. 全部实体**逻辑删除**；会话绑定 `checkpoint_thread_id`，便于后期统一清理。
>
> DDL 见 `deploy/sql/business_schema.sql`（幂等，可直接 `psql -f` 执行）。

## 1. 表清单与关系

```
users 1 ── n sessions 1 ── n messages              （messages 按月分区，长期保留）
  │             │
  │             └── n session_events               （过程事件，保留 30 天）
  │             └── n message_idempotency          （前端重发幂等键）
  ├── n user_identities                            （多登录方式扩展位）
  └── n user_tokens                                （JWT refresh 落库，可撤销）

monitor_components / monitor_field_meanings / user_token_usage   （监控平台配置，自 checkpoint 库迁入）
schema_migrations                                                （增量迁移版本记录）
```

| 表 | 用途 | 保留策略 |
|----|------|---------|
| `users` | 用户（真实账号） | 逻辑删除，长期保留 |
| `user_identities` | 登录方式映射（local / wechat / oidc…） | 跟随用户 |
| `user_tokens` | JWT 令牌（refresh 哈希落库） | 过期 + 7 天后物理清理 |
| `sessions` | 会话元数据 + 绑定 checkpoint thread | 逻辑删除；后台任务按"陈旧"策略清理 |
| `messages` | 消息（user/assistant/clarify/answer/error） | **长期保留**，按月分区 |
| `message_idempotency` | `client_msg_id` → 已落库消息 | 长期保留（可随消息归档） |
| `session_events` | 步骤/工具/计划等过程事件（前端回放） | **30 天**（`cleanup_session_events()`） |
| `monitor_*` | 监控组件配置 / 槽位含义 / 用户 token 累计 | 长期保留 |
| `schema_migrations` | 迁移版本 | 长期保留 |

## 2. 关键设计点

### 2.1 消息表与 checkpoint 解耦
- `sessions.checkpoint_thread_id` 显式保存 thread_id（默认 = `sessions.id::text`），
  **checkpoint 库只管 agent 运行态**，业务库管"用户可见事实"；
- checkpoint 被压缩/过期/清理时，历史消息**不受影响**；
- 清理链路（后期定时任务）：标记 `sessions.deleted_at` → 应用侧按 `checkpoint_thread_id`
  调 `checkpointer.adelete_thread()` → 业务库消息仍保留（审计/合规）。

### 2.2 逻辑删除
- 所有业务实体带 `deleted_at`；唯一性用 **partial unique index**（`WHERE deleted_at IS NULL`），
  逻辑删除后 username / thread 可复用；
- 查询默认追加 `deleted_at IS NULL`；对外接口不暴露物理删除。

### 2.3 原子写入（`append_message` 函数）
一条对话轮次的两条消息（user + assistant）在**同一事务**内调用 `append_message`：
- 进入即 `ensure_message_partition_for(now())`，**分区不存在自动补建**（不依赖定时任务，插入永不失败）；
- 行锁 `UPDATE sessions` 分配 `seq` 并刷新 `message_count / last_message_at / last_preview`（避免 `MAX(seq)` 竞态）；
- `client_msg_id` 幂等：前端重发返回既有消息（不是报错、也不是重复写）；
  幂等键由**独立的 `message_idempotency` 小表**承载 —— 分区表无法对 `client_msg_id` 建全局唯一索引；
- 函数异常分支会清掉"只写了一半"的幂等占位，避免后续重发被误判为已存在；
- 会话级计数与预览直接可用于列表页，无需回表 `messages`。

### 2.4 messages 按月分区
- `PARTITION BY RANGE (created_at)`，主键必须是 `(id, created_at)`（分区表约束）；
- 分区命名 `messages_YYYYMM`；`ensure_message_partitions(months_back, months_ahead)` 批量预建；
- 分区索引：父表上创建索引会自动挂到新分区（`uq_messages_session_seq` / `idx_messages_session_seq` / `idx_messages_user_time` / GIN 全文索引）；
- **同会话同序号唯一性**：唯一索引必须含分区键（`session_id, seq, created_at`），
  真正语义由 `append_message` 的会话行锁保证；
- 建议 pg_cron 或后端任务每月执行 `SELECT ensure_message_partitions(1, 3)`（双保险）。

### 2.5 认证：账号密码 + JWT
- `users.password_hash` 存 **Argon2id/bcrypt** 哈希（不存明文）；
- 登录成功签发 **access token（短，内存/前端）+ refresh token（长，落 `user_tokens`）**；
- `user_tokens` 存 `jti` + `token_hash`（SHA-256），支持：撤销单设备、改密踢下线、设备列表；
- access token 校验只验签 + `exp`（无状态）；refresh 校验必须查库（`revoked_at IS NULL AND expires_at > now()`），
  并**旋转 refresh（旧的置 `revoked_at`）**，防重放；
- 接口从认证上下文取 `user_id`（缺失 401；不落匿名会话）。

### 2.6 可扩展性
- 枚举一律用 `TEXT + CHECK`（新增类型只需 `ALTER TABLE ... DROP/ADD CONSTRAINT`，不必改 enum 类型）；
- `meta JSONB` / `payload JSONB` 承载未来字段（澄清选项、计划快照、错误详情）；
- `users.roles TEXT[]` 预留权限模型；`user_identities` 预留第三方登录；
- `messages` 已含 token/latency 字段，token 计费统计可直接按用户+模型聚合；
  `user_token_usage` 作为历史兼容表迁入，后续可由 `messages` 聚合替代（届时 `user_id` 改用 `users.id`）。

## 3. 接口与表映射

| 接口 | 表操作 |
|------|--------|
| `POST /auth/register` `POST /auth/login` | `INSERT users` / 校验 `password_hash` + `INSERT user_tokens` |
| `POST /auth/refresh` `POST /auth/logout` | `user_tokens` 旋转 / 置 `revoked_at` |
| `POST /sessions` | 校验用户 → `INSERT sessions`（`checkpoint_thread_id = id::text`） |
| `GET /sessions` | `sessions` 键集分页（`last_message_at DESC, id DESC`，`deleted_at IS NULL`） |
| `GET /sessions/{id}/messages` | `messages` 按 `seq` 倒序取页、正序返回（仅 `deleted_at IS NULL`） |
| `POST /sessions/{id}/chat` | 流开始写 user 消息、结束写 assistant 消息（`append_message`），失败也落 `kind=error` |
| `PATCH /sessions/{id}` | 改 `title` / `status`（archive） |
| `DELETE /sessions/{id}` | 逻辑删除（`deleted_at=now()`），不动物理数据 |
| 后台任务 | 月度建分区；`cleanup_session_events(30)`；陈旧会话逻辑删除 → `adelete_thread` |

## 4. 配置与迁移

- 新增业务库连接（**与 checkpoint 库分开**）：
  - `config.yaml`：`business_database.url: $BUSINESS_DATABASE_URL`
  - `.env`：`BUSINESS_DATABASE_URL=postgresql://user:pass@host:5432/agent_business`
  - 认证相关 `.env`：`JWT_SECRET` / `JWT_ACCESS_TTL_MINUTES` / `JWT_REFRESH_TTL_DAYS`
- 代码侧新增 `app/session/store.py`（连接池 + 上表 CRUD），与 `app/monitor/store.py` 同模式；
- 认证侧 `app/auth/`（密码哈希、JWT 签发/校验、FastAPI 依赖 `current_user`）；
- **monitor 三表迁移**（checkpoint 库 → 业务库），见 `deploy/sql/business_schema.sql` 末尾运维 SQL：
  - 方式一：`pg_dump -t monitor_components -t monitor_field_meanings -t user_token_usage --data-only` → `psql -d agent_business -f`
  - 方式二：同实例跨库用 dblink/FDW `INSERT ... SELECT`
  - 迁移后 `app/monitor/store.py` 指向业务库连接池。

## 5. 实施顺序（P0 已完成，见 docs/会话持久化方案.md §9 实施状态）

1. **建库执行 DDL**（你执行 `deploy/sql/business_schema.sql`）；
2. 配置接入：`business_database` 段 + `.env`（两个配置模板同步）；
3. 后端：`app/session/`（store + `AgentService` 会话改造）、路由 `GET /sessions`、`GET /sessions/{id}/messages`、`PATCH`、`DELETE`；chat 落库（user+assistant+error）；
4. 认证：`app/auth/`（注册/登录/刷新/登出 + `current_user` 依赖），接口按 `user_id` 过滤；
5. 监控：`app/monitor/store.py` 切到业务库；
6. 前端：登录态 + 会话列表 + 历史回显 + 当前会话 id 持久化（`localStorage` 仅存 id/jwt，真实数据在服务端）；
7. 后台任务（暂缓）：月度分区维护、事件 30 天清理、陈旧会话清理。

## 6. 已确认决策

| # | 事项 | 结论 |
|---|------|------|
| Q1 | 认证方式 | **账号密码 + JWT**（`users` + `user_identities` + `user_tokens`） |
| Q2 | monitor 三张表 | **迁入业务库**（同一连接池，避免两库混杂） |
| Q3 | `messages` 分区 | **按月 RANGE 分区**（`messages_YYYYMM`，自动补建 + 定时预建双保险） |
| Q4 | `session_events` 保留期 | **30 天**（`cleanup_session_events(30)` 已提供；后端定时任务暂不实现） |
