# 打点设计（app/core/tracking）

打点（tracking）用于记录系统关键事件，统一输出 **protobuf wire format** 二进制，
便于后续接入日志/消息/数仓等下游。实现位于 `app/core/tracking/`（纯 Python，零额外依赖）。

**打点与执行日志分离**：打点不写入执行日志（`logs/app.log`，loguru），而是默认写入独立的
**数据日志文件**（config.yaml `tracking.output`，默认 `logs/tracking.data`），每行一条：

```
{ISO 时间} {base64(protobuf)}
```

行内保持纯数据（无日志文本），由下游（Kafka / 数仓 / 离线分析）消费；需要其他输出时
给 `Tracker` 传入自定义 `sink` 即可。

## 1. 数据结构

与以下 Go 结构体一一对应（`Content` 外层，`Ext` 为点位信息）：

```go
type Content struct {
    Type   string `json:"type"`   // 打点类型
    Page   string `json:"page"`   // 业务名称
    Source string `json:"source"` // 来源
    Ext    *Ext   `json:"ext"`    // 点位信息
}

type Ext struct { // 点位信息：P0-P14，按业务名称（page）分配不同含义
    P0  string `json:"p0"`
    P1  string `json:"p1"`
    // ... P2-P13 ...
    P14 string `json:"p14"`
}
```

### protobuf 等价定义与字段编号

```proto
syntax = "proto3";

message Content {
  string type   = 1;  // 打点类型
  string page   = 2;  // 业务名称
  string source = 3;  // 来源
  Ext    ext    = 4;  // 点位信息（嵌套 message）
  string model  = 5;  // 模型角色名（监控按 model 分组/对比）
}

message Ext {
  string p0  = 1;
  string p1  = 2;
  // ... p2..p13 = 3..14 ...
  string p14 = 15;
}
```

编码规则（标准 protobuf wire format）：
- 所有字段均为 string / 嵌套 message → wire type 2（length-delimited）：`tag + varint(len) + UTF-8 bytes`
- 标签 `tag = (field_number << 3) | 2`，按 varint 编码（字段号 ≤ 15 时标签为单字节）
- **空字符串 / 空 Ext 自动省略**（protobuf 默认值，解码端还原为 `""` / 缺省）

## 2. 打点类型（Content.type）

定义于 `app/core/tracking/constants.py` 的 `TrackingType`：

| 枚举值 | 值 | 含义 |
|--------|-----|------|
| `CLICK` | `click` | 点击 |
| `EXPOSURE` | `exposure` | 曝光（页面/模块被展示） |
| `VIEW` | `view` | 浏览/查看 |
| `SESSION_START` | `session_start` | 会话开始 |
| `SESSION_END` | `session_end` | 会话结束 |
| `MESSAGE_SEND` | `message_send` | 用户发送消息 |
| `MESSAGE_RECEIVE` | `message_receive` | 助手回复消息 |
| `PLAN_CREATE` | `plan_create` | 创建新计划 |
| `PLAN_UPDATE` | `plan_update` | 更新现有计划 |
| `PLAN_COMPLETE` | `plan_complete` | 计划完成（反思通过给出最终答案） |
| `CLARIFY` | `clarify` | 发起澄清提问 |
| `STEP_START` | `step_start` | 子任务开始执行 |
| `STEP_COMPLETE` | `step_complete` | 子任务执行完成 |
| `TOOL_CALL` | `tool_call` | 执行节点调用工具 |
| `TOOL_RESULT` | `tool_result` | 工具返回结果 |
| `EVALUATION` | `evaluation` | LLM-as-Judge 评估 |
| `LATENCY` | `latency` | 耗时统计 |
| `ERROR` | `error` | 错误事件 |
| `JOIN` | `join` | 一次完整请求（调用模型到返回，p0=总耗时ms） |
| `TOKEN_USAGE` | `token_usage` | Token 消耗（p0=总 token，p1=输入，p2=输出，p3=费用(元)） |

## 3. 业务名称（Content.page）

定义于 `TrackingPage`。**Ext 槽位的含义按 page 分配**（见第 5 节）：

| 枚举值 | 值 | 含义 |
|--------|-----|------|
| `CHAT` | `chat` | 对话 |
| `PLAN` | `plan` | 规划节点 |
| `EXECUTE` | `execute` | 执行节点 |
| `EVALUATION` | `evaluation` | 评估器 |
| `KNOWLEDGE` | `knowledge` | 知识库 |
| `SYSTEM` | `system` | 系统/框架层 |
| `CALL_MODEL` | `call_model` | 调用模型（一次完整请求，p0=总耗时ms） |
| `TOKEN` | `token` | Token 消耗（p0=总 token，p1=输入，p2=输出，p3=费用） |

## 4. 来源（Content.source）

定义于 `TrackingSource`：`web`（Web 前端）、`server`（服务端）、`app`（移动端/客户端）、`internal`（内部任务/后台）。

## 5. 点位信息（Ext P0-P14）槽位约定

P0-P14 共 15 个字符串槽位，**具体含义由业务名称（page）决定**。以下为推荐约定，
新增业务时在表格中补充并保持同一业务内槽位含义稳定。

### 5.1 通用约定（各业务共用）

| 槽位 | 通用含义 |
|------|----------|
| P0 | 主对象 ID（plan_id / session_id / doc_id / 任务 ID） |
| P1 | 数量 / 计数 |
| P2 | 状态 / 动作 |
| P3 | 耗时（毫秒） |
| P4 | 错误码 / 补充信息 |
| P5-P9 | 业务自定义 |
| P10-P14 | 预留 |

### 5.2 按业务名称分配

| 槽位 | `plan` 规划 | `execute` 执行 | `chat` 对话 | `evaluation` 评估 |
|------|-------------|----------------|-------------|--------------------|
| P0 | plan_id | task_id（plan_id） | session_id | evaluator 名 |
| P1 | 子任务数量 | agent 名 | 消息数 | 指标名（metric） |
| P2 | action（create/update/complete） | 状态（completed/failed） | 模型角色名 | 得分 |
| P3 | 规划耗时(ms) | 执行耗时(ms) | 响应耗时(ms) | 评估耗时(ms) |
| P4 | 澄清问题摘要 | 工具名 | 错误码 | 是否通过（true/false） |
| P5-P9 | 自定义 | 工具参数摘要 | 自定义 | 自定义 |
| P10-P14 | 预留 | 预留 | 预留 | 预留 |

## 6. 使用示例

```python
import asyncio

from app.core.tracking import (
    TrackingExt,
    TrackingPage,
    TrackingSource,
    TrackingType,
    Tracker,
    encode_tracking_content,
    track,
)

async def main() -> None:
    # 1) 便捷入口：全局默认 Tracker（写入独立数据日志 logs/tracking.data）
    payload = await track(TrackingType.TOOL_CALL, TrackingPage.EXECUTE, p0="web_search", p3="120")
    print("payload bytes:", payload.hex())

    # 2) 自定义 Tracker：替换 sink 接入真实数据链路（Kafka / HTTP / 文件）
    def sink(payload: bytes) -> None:
        print(f"[sink] {len(payload)} bytes -> {payload.hex()}")

    tracker = Tracker(source=TrackingSource.SERVER, sink=sink)
    await tracker.track(TrackingType.PLAN_CREATE, TrackingPage.PLAN, ext=TrackingExt(p0="plan-1", p1="3"))
    await tracker.aclose()  # 使用默认数据日志 sink 时，结束前关闭文件

    # 3) 直接编码（不经过 Tracker）
    content = TrackingContent.from_dict(
        {"type": "error", "page": "execute", "source": "server", "ext": {"p0": "task-1", "p4": "timeout"}}
    )
    raw = encode_tracking_content(content)

asyncio.run(main())
```

## 7. 解码查看（protobuf 工具 / CLI）

**为什么日志内容是 base64？** 数据日志是逐行**文本**文件，而 protobuf 是**二进制**——
二进制字节无法直接写入文本行，因此每行把 protobuf 字节做 base64 编码：

```
{ISO 时间} {base64(protobuf Content bytes)}
```

**base64 只是"二进制进文本行"的传输编码，不是数据本身**；`base64 -d` 之后就是标准
protobuf wire-format 字节，可用任何 protobuf 工具解析。

### 7.1 命令行查看工具（推荐）

```bash
uv run python -m app.core.tracking logs/tracking.data      # 逐行解码为 JSON
uv run python -m app.core.tracking --payload "Cgl0b29s..." # 解码单条 base64
cat logs/tracking.data | uv run python -m app.core.tracking # 从 stdin 读取
```

输出示例：

```json
{"time": "2026-08-21T14:30:23.899+08:00", "type": "tool_call", "page": "execute", "source": "server", "ext": {"p0": "web_search", "p3": "120", "p1": "", ...}}
```

### 7.2 用 protoc（官方 protobuf 工具）

schema 定义在 `app/core/tracking/tracking.proto`：

```bash
# 单条：base64 → 二进制 → protoc 解码
echo "Cgl0b29sX2NhbGw..." | base64 -d | protoc --decode=tracking.Content app/core/tracking/tracking.proto
```

### 7.3 代码里解码

```python
from app.core.tracking import decode_tracking_content

content = decode_tracking_content(payload_bytes)   # bytes → TrackingContent
print(content.type, content.page, content.ext.p0)
```

## 8. 监控平台（Web /monitor）

Web 项目新增「监控」页（`web/src/components/MonitorView.vue`），后端接口在
`app/monitor/`（/monitor/*，配置存 PostgreSQL）：

- **监控组件**：用户可动态添加/编辑/删除；每个组件配置 = 业务名称（page）+ 指标槽位
  （p0..p14，可按 page 配置含义）+ 模型过滤 + 统计方式（和值/平均值）+ 展示粒度
  （分钟级/小时级）；组件配置持久化到 PG（`monitor_components` 表）。
- **时间范围**：近 30 天 / 近 7 天 / 昨天 / 自定义起止时间；数据按分钟/小时展示。
- **按模型对比**：同一组件下未指定模型时按 model 分组画多条折线，可对比不同模型
  的 P0（如耗时）/ P1（如优化指标）差异。
- **字段含义**：P0-P14 在不同 page 下的含义可在监控平台配置（存 `monitor_field_meanings`），
  配置后组件与图表上展示对应含义（如 P1=评估得分，可看某模型多次调用平均得分）。
- **Token 监控**：每次请求打 `token_usage` 事件（按模型区分输入/输出/总 token/费用），
  用户累计消耗存 PG（`user_token_usage` 表，当前以 session_id 代指用户）；
  单价在 config.yaml `token_pricing` 配置（元 / 1K tokens，未配置按 0 计费）。

## 9. 扩展指引

- **新增打点类型 / 业务名称**：在 `constants.py` 补充枚举值，并在本文第 2/3/5 节补充含义说明。
- **接入真实数据链路**：无需改动模型与编码器，替换 `Tracker` 的 `sink`（同步回调或协程均可）即可，
  例如批量缓冲后上报、投递 Kafka、写入数仓等；默认数据日志文件每行一条（ISO 时间 + base64），
  可直接被 filebeat / flink / spark 等按行消费。
- **字段编号**：`Content` 为 1-4、`Ext` 为 1-15，**已发布后不可修改字段编号/类型**（protobuf 兼容性约束）；
  规范 schema 见 `app/core/tracking/tracking.proto`（protoc 可直接使用）。
- **数据日志路径**：config.yaml `tracking.output`（默认 `logs/tracking.data`），与执行日志 `logs/app.log` 分离。
