# 消息流转与用户展示方案（Plan 节点 transcript / UI 双轨）

> 背景：Plan 节点内的 `create_agent` 是主 agent，它的消息是**LLM 上下文的主体**；
> 用户展示又要求"干净"。这两个诉求若在同一份 `messages` 上满足，就会互相破坏——
> 本方案把它们拆成**双轨**：`messages`（append-only transcript，保 KV 缓存）
> + `ui_messages` / SSE 事件（对外口径）。

## 1. 两条硬约束

| 约束 | 说明 |
|------|------|
| **C1 前缀稳定（KV cache）** | 缓存命中以「system prompt + messages 前缀」为单位。任何对**既有**消息的删除/改写/重排/换 id 都会让该点之后全部 cache miss，按全价重算。→ 规则：**append-only**。 |
| **C2 展示干净** | 用户不应看到 `Returning structured response: …`、ToolMessage、内部 tool_calls、思考流水。→ 规则：**展示与存储解耦**，展示走独立通道。 |

结论：`messages` 只服务 LLM（保留全部原文），对外内容走 `ui_messages` + SSE `custom` 事件。

## 2. 现状问题（逐条对照代码）

1. **澄清分支改写历史**：`plan_model_node._clean_clarification_messages()` 把
   `[AIMessage(tool_calls) + ToolMessage(问题)]` 替换成一条干净 `AIMessage` —— 每轮澄清都会
   改写已有消息 → 破坏 C1（该点之后全量重算）。
2. **结构化输出的消息会进 state**：LangChain structured-output fallback 产出
   `AIMessage(tool_calls=PlanOutput)` + `ToolMessage("Returning structured response: …")`，
   被 `agent_msgs` 原样写回；前端只能用"从后往前找最后一条非空 AIMessage"兜底，容易被 dump 污染。
3. **前端与内部消息强耦合**：`App.vue` 依赖 `values`（状态快照）+ `messages`（token 增量）
   两种流来拼气泡；任何内部消息结构调整都会影响上屏。
4. **判定逻辑本身是对的**：`has_clarification` 用「本轮新增消息 id 差集」判定（而不是看最后一条），
   这部分保留；问题只在**展示与回写**上。
5. **plan 分支回写 `agent_msgs`（历史+新增）**：依赖 `add_messages` 的 id 去重，语义正确，
   但"新增"应显式用 id 差集挑出来，避免把历史重复写回造成的潜在噪声。

## 3. 设计原则

- **P1 Append-only**：`messages` 只追加、不改写、不删除、不重排，message id 保持不变。
- **P2 双轨**：`messages`=内部真相（给 LLM）；`ui_messages`=对外真相（给前端/回放）。
- **P3 判定用数据，展示用事件**：分支判定（结构化 / 澄清 / 直接回复）只看结构化结果与本轮新增
  tool_calls；对外展示一律由节点 emit 事件，不由"消息内容"反推。
- **P4 结构化输出只当数据**：`PlanOutput` 从 `structured_response` / AIMessage 解析即可，
  **不把它转成用户消息**；原始 tool 消息保留在 transcript 但永不展示。

## 4. 状态与返回契约

```python
class ThreadState(TypedDict, total=False):
    messages: Annotated[list[BaseMessage], add_messages]  # append-only transcript（KV 前缀）
    ui_messages: Annotated[list[dict], add_ui_messages]   # 对外展示项（think/plan/step/clarify/answer）
    plan_tasks: Annotated[list[SubTask], merge_plan_tasks]
    completed: bool
    final_answer: str
    pending_clarification: dict | None                    # 待澄清快照（问题/类型/选项）
    # Send 注入：plan_id / task_name / task_desc
```

节点每轮返回（关键：只回**本轮新增** transcript 尾部）：

```python
{
  "messages": new_transcript_msgs,     # = 本轮新增（id 差集），原顺序、含 tool 消息
  "ui_messages": emitted_ui_events,    # 与 SSE 同步的对外副本（供历史回放）
  "plan_tasks": ... / Overwrite(...),
  "completed": True/False,
  "pending_clarification": {...} | None,
}
```

## 5. 对外事件协议（SSE `custom`）

前端**只消费 custom 事件**（`values`/`messages` 逐步下线）：

```jsonc
{"type":"think",   "content":"📋 分析需求，制定执行计划...", "trace_id":"..."}
{"type":"plan",    "action":"create|update", "title":"...", "tasks":[{"plan_id":"task1","name":"...","status":"not_started","skill_id":"query-weather","sop_step":"step-01"}]}
{"type":"step",    "plan_id":"task1", "status":"in_progress|completed|failed", "summary":"..."}
{"type":"clarify", "content":"问题文本", "clarification_type":"missing_info", "options":["..."], "context":"..."}
{"type":"answer",  "content":"最终答复（纯文本）", "final":true}
{"type":"end"}
```

- 打字机效果：可选保留 `messages` 增量流，仅**节流转发**为 `{"type":"streaming","delta":"..."}`，
  **不落库、不参与 transcript**。
- 历史回放：新增 `GET /sessions/{id}/ui-messages`（读 `ui_messages`），前端不再回放内部 transcript。

## 6. 两类分支的处理（对应问题 2）

### (a) 结构化输出 = 创建/更新任务

- **transcript**：原样追加本轮新增（`AIMessage(tool_calls=PlanOutput)` + 结构化 ToolMessage）。
  不替换、不清洗 → 前缀稳定、悬空 tool call 不存在。
- **判定**：`_extract_plan_output(agent_output)`（已实现）→ `action=create/update/complete`。
- **对外**：
  - `plan` 事件（任务清单，含 `skill_id/sop_step`，前端渲染 TODO/进度）；
  - `action=complete` 时追加 `answer` 事件（并 append 一条干净 `AIMessage(answer)` 到 transcript，
    作为"助手正式回复"的语义锚点——append-only，不影响前缀）。
- 明确禁止：把结构化 dump 包装成用户可见消息。

### (b) 澄清工具命中 = 用户描述不清

- **transcript**：原样保留 `AIMessage(tool_calls=ask_clarification)` + `ToolMessage(格式化问题)`。
  **取消** `_clean_clarification_messages()`（它改写历史、破坏缓存；保留 ToolMessage 后也不再有悬空问题）。
- **判定**：本轮新增消息中存在 `ask_clarification` tool_call（现有逻辑保留）。
- **对外**：`clarify` 事件（问题/类型/选项/背景）→ 前端渲染澄清卡片；`pending_clarification` 落状态。
- 用户回答作为下一条 `HumanMessage` 追加 → 下一轮 `has_clarification` 只看新增，不会误判。

### (c) 直接回复（无结构化、无澄清）

- transcript 原样保留；对外 `answer` 事件。

## 7. Plan 节点消费 `agent.astream` 的推荐骨架

```python
input_ids = {m.id for m in messages if getattr(m, "id", None)}
new_msgs: list[BaseMessage] = []
ui_events: list[dict] = []
structured = None

async for mode, payload in inner_agent.astream(
    input={"messages": messages}, config=config,
    stream_mode=["updates", "custom", "messages"],   # messages 可选（仅流式转发）
):
    if mode == "updates":
        for update in payload.values():              # 各内部节点/工具的 state 更新
            new_msgs.extend(update.get("messages", []))
            structured = update.get("structured_response") or structured
    elif mode == "custom":                           # 内部 think/进度 → 直接透传为 ui 事件
        ui_events.append(payload)
    elif mode == "messages":                         # 仅节流转发，不落库
        forward_streaming_delta(payload)

# 去重 + 只保留本轮新增，保持原始顺序
seen, transcript = set(input_ids), []
for m in new_msgs:
    mid = getattr(m, "id", None)
    if mid and mid in seen:
        continue
    seen.add(mid)
    transcript.append(m)
```

要点：
- **不要用 `messages` 模式的增量重建 transcript**（会丢 `tool_calls` / ToolMessage，导致结构损坏）；
  transcript 以 `updates` / 终态 state 为准。
- `messages` 模式只用于 UI 打字机效果，且节流。
- 结构化结果优先取 `structured_response`（fallback 模式），再回退解析最后一条 AIMessage（现有 `_extract_plan_output`）。

## 8. 前端改造点（`web/src/App.vue`）

- 删除 `values` 兜底「从后往前找非空 AIMessage」与 `messages` 累加逻辑；
- 改为事件驱动渲染：`think`→思考条、`plan`→任务清单、`step`→步骤状态、`clarify`→澄清卡片（含选项按钮）、
  `answer`→助手气泡、`end`→收尾；
- 历史回放改用 `/sessions/{id}/ui-messages`；
- 澄清卡片的用户点击/输入统一走现有 chat 接口（回复作为 `HumanMessage` 追加）。

## 9. KV 缓存收益与例外

- append-only 后，同会话连续追问：前缀不变 → 缓存命中；新增部分（本轮 user + 本轮 agent 新增）才计费。
- 反例（现状）：澄清替换、结构化消息被清洗都会让缓存从改写点失效。
- **唯一例外**：未来的 `summarization` 节点（当前为 `pass` 空实现）压缩历史时必须改写前缀，
  该轮需接受一次性全量重算；建议压缩后打点记录 `cache_break=summarization`，便于归因。

## 10. 迁移步骤与验收

**迁移**
1. 双写：保留现有 `values/messages` 流，同时新增 `ui_messages` + `custom` 事件（不改判定逻辑）；
2. 前端切事件（灰度），确认展示无回归后删除 values 兜底；
3. 删除 `_clean_clarification_messages()`，澄清改为「保留 transcript + clarify 事件」；
4. `agent_service` 增加 `/sessions/{id}/ui-messages`。

**验收**
- 同会话连续 3 轮追问：transcript 前缀不被改写（可用 Langfuse / provider 返回的 cached tokens 对比）；
- 前端不出现 `Returning structured response` / tool dump；
- 澄清一轮后 transcript 只 +2 条（AI+Tool），第二轮不再误判为澄清；
- 结构化输出后任务清单与最终答复展示正确；
- 失败/恢复链路（skill errors）仍能按 `step` 事件呈现。


## 11. 本轮实现落点（代码）

- **统一输出层 `app/agents/events.py`**：
  - `EventType`（thinkMessage / thinking / tool_call / tool_result / plan / step / clarify / answer / error / end）、
    `StepStatus`、`Output`（`think/thinking/plan/step/tool_call/tool_result/clarify/answer/error/end`，
    无运行上下文时安全降级为 no-op）、`ToolCallAccumulator`（流式 tool_call_chunks → 完整调用）、
    `humanize_tool_call`；
  - 节点不再直接 `writer({...})` / 不再拼魔法字符串（`app/agents/nodes/_emit.py` 草稿已删除，
    `nodes/constants.py` 的 `THINK_MES` 指向 `EventType.THINK`，单一来源）。
- **规划节点 `plan_model_node`**：`create_agent` 改为 `astream(stream_mode=["messages","updates"])` 消费——
  `messages` 流转发增量（打字机）+ 累积工具调用事件；`updates` 流收集 transcript 并捕获
  `structured_response` 与 `ask_clarification` 参数；分支结果统一由 `_apply_plan_result` 落库并发事件
  （`plan` / `answer` / `clarify`）。
- **执行节点 `general_agent`**：同样改为流式消费，向前端输出执行过程——
  `step(started/completed/failed)` + `tool_call` / `tool_result`（含 plan_id/skill_id/sop_step）+ 增量文本。
- **前端**：`App.vue` 消费 `step/tool_call/tool_result/plan/thinking` 事件形成"执行过程"列表，
  `ChatArea.vue` 新增 `progress` 渲染；`thinkMessage` 行为保持不变（向后兼容）。

> 尚未迁移：`messages` 仍按既有方式写回（澄清仍以干净 AIMessage 对用户回复）。
> 第 6 节的"保留原始澄清 pair（append-only）"与前端全事件化属于下一步，需要前端切流后再改。
