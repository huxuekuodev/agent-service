# 语音通话方案（页内与 Agent 语音对话）

> 形态：**在页面里按一下「📞 语音通话」，用说话代替打字和 Agent 对话**——不是拨打真实电话号码（PSTN）。
> 对话内容与文字聊天同一条会话、同一份上下文、同一套中断/恢复链路，语音消息同样进历史。

## 1. 数据流

```
🎙️ 麦克风
   └─ 浏览器原生语音识别（Web Speech API，边说边出字）
        └─ 整句定稿 → POST /sessions/{id}/chat  { message, voice: true }   （复用现有 SSE）
             └─ 规划/执行图（同一 thread_id，上下文与文字聊天完全一致）
                  └─ 答复文本 → 服务端**按句切块** → 硅基 CosyVoice2 逐块合成
                       └─ SSE 事件 voice_audio（每块一个 base64 mp3）
                            └─ 前端语音队列顺序播放；播放期间界面显示文字字幕
```

- **识别在浏览器**：音频不出本机、零成本、延迟最低（部分结果 ~200ms 就能上屏）；
- **合成在服务端**：音色统一、跨端一致、可审计（同一条答复文字也会落库）；
- **传输复用 SSE**：不新开 WebSocket，鉴权/落库/中断/恢复全部沿用既有链路。

## 2. 选型与实测（决定方案的关键数字）

| 能力 | 方案 | 实测 | 结论 |
|------|------|------|------|
| TTS | 硅基 CosyVoice2（`/audio/speech`，OpenAI 兼容） | 20 字 **0.53s** / 45 字 **0.93s** / 90 字 **1.48s**（整段返回，延迟随长度线性） | ✅ 采用，**必须按句切块** |
| ASR | 硅基 SenseVoiceSmall（`/audio/transcriptions`） | 3 秒音频 **45s**、6 秒音频 **>60s 超时** | ❌ 服务端不可用 |
| ASR | 浏览器 Web Speech API | 边识别边出字，部分结果 ~200ms | ✅ 采用（Chrome/Edge） |

> ASR 那组数字也解释了一个坑：**复用失效的 keep-alive 连接会出现 20–80s 假死**。
> 所以服务端的 TTS 客户端把 `keepalive_expiry` 设短（5s），并在超时/连接错误时**换新连接重试一次**。

## 3. 分句切块（长文本不整段合成）

实现见 `app/voice/audio.py:split_for_speech`，策略：

1. 先清洗 Markdown（标题符/强调符/列表符/代码块/表格线都不朗读）；
2. 按句末标点切句，**过短的句子并到下一句**（避免一句一顿的机械感，`chunk_min_chars`）；
3. **首块更短**（`first_chunk_max_chars`，默认 30 字）：第一声尽快响，这是通话体感的关键——
   首句超过上限时先按逗号切一刀；
4. 单句仍超长时按逗号再切，再不行按字符硬切（保护单次请求时长）；
5. 总块数封顶（`max_chunks`，默认 20），超出丢弃并提示「其余请看界面文字」。

效果（实测）：一句 47 字答复 → 块 1 = 30 字、块 2 = 17 字；**第一块音频约 0.6s 后即可播放**，
而不是等整段（若整段 200 字，用户要干等 2–3 秒才听到第一个字）。

## 4. 延迟预算（用户体感）

| 阶段 | 耗时 | 说明 |
|------|------|------|
| 说完 → 识别定稿 | ~0.3–0.8s | 浏览器静默判停后给最终结果 |
| 图执行（规划/执行/技能/沙箱） | 数秒~数十秒 | **当前瓶颈**，与文字聊天相同 |
| 首块 TTS | ~0.5–0.9s | 30 字以内 |
| 后续块 | 边播边合成 | 播放第 1 块时第 2 块已在合成 |

配合**语音模式提示词**（`<VoiceMode>`，见 `app/agents/nodes/plan_model_node.py`）：语音请求会要求节点
用口语化短句作答（1–2 句、≤80 字、不要 Markdown/表格/代码块）。实测同一问题：
语音模式 47 字（2 块音频），文字模式 149 字（朗读要 3 倍时间）——**答得短 = 说得快**。

## 5. 事件与降级

| 事件 | 含义 | 前端处理 |
|------|------|---------|
| `voice_audio` | 一块语音（`seq` 序号、`text` 对应文本、`audio` base64 mp3、`final`） | 入队顺序播放，同时显示字幕 |
| `voice_end` | 本轮语音播报结束 | 回到「聆听中」 |
| `voice_unavailable` | 服务端合成不可用（未启用/没 Key/失败/无内容） | **降级为浏览器内置朗读**（`speechSynthesis`，免费即时），通话不静默 |
| `interrupt` | 计划等待确认 | 卡片出现；下一句语音走 `/resume`：说「继续」= 无意见执行，其他内容 = 提意见重排 |

浏览器不支持语音识别（Firefox）时，通话面板会明确提示改用 Chrome/Edge 或直接打字，文字链路照常可用。

## 5.1 事件载荷形状（踩过的坑）

SSE 事件有两类形状，混用会**静默失效**（现象：界面有文字、没有声音）：

| 事件 | 形状 | 前端读法 |
|------|------|---------|
| `custom`（thinkMessage/plan/step/answer/error） | **嵌套** | `event.data.type` / `event.data.content` |
| `interrupt` | **嵌套** | `event.data.interrupt_id` / `event.data.payload` |
| `voice_audio` | **扁平** | `event.audio` / `event.format` / `event.text` / `event.seq` |
| `voice_unavailable` / `voice_end` / `end` | **扁平** | `event.type` / `event.msg` |

`voice_audio` 的服务端载荷：`{type, seq, text, format:"mp3", audio:<base64>, final}`（音频字段就在顶层）。
前端若读到空音频，会在控制台告警并**自动用浏览器朗读兜底**（不再静默没声音）。

另外：浏览器自动播放策略要求"用户手势里播过一次"，因此点「📞 语音通话」时会先播一段静音 WAV 解锁，
否则程序化播放合成语音可能被拦截（控制台会提示"播放被拦截"）。

## 5.2 「有确认提示、没有结果语音」的两个坑（已修）

1. **前端漏带 `voice` 标记**：计划确认的语音来自第一轮 `POST /chat {voice:true}`，而"确认后执行"这一轮
   如果走的是另一条调用路径（卡片确认 / 语音说「继续」）却没带 `voice`，后端就不会合成——
   现象正是"中断有声音、结果没有"。现在 `runStream()` 的 `voice` **默认跟随"是否在通话中"**，
   任何调用路径都不会漏（结构上防复发，而不是每个调用点自己记得）。
2. **语音说「继续」被当成"意见"**：语音确认时若把"继续"当作 `custom` 反馈提交，会触发**重新规划**
   而不是执行。现在前端用 `isContinueIntent()` 判定（继续/可以/开始/确认… 且长度 ≤12）→ 走"无意见执行"。

顺带修了一个后端死路：审查轮模型返回**空输出**（既没答案也没新任务）时，图会静默结束，
用户既看不到文字也听不到语音（`voice_unavailable: 本轮没有可播报的内容`）。现在
`plan_model_node` 有兜底：先用已完成任务的真实结果汇总成答复，确实没有结果时给一句诚实提示；
同时打 warning 日志（含 `plan_output` 摘要）便于排查。

## 5.3 通话界面（动效 / 字幕 / 卡片 / 打断）

四种状态各有独立视觉与文案（`web/src/components/CallPanel.vue`）：

| 状态 | 动效 | 文案 | 可用操作 |
|------|------|------|---------|
| 聆听中 | **麦克风电平驱动的波形**（`AnalyserNode` 实时音量 × 中间高两边低的包络） | 我在听，请说 | 静音 / 挂断 |
| 思考中 | 紫色呼吸波纹 + `· · ·` 闪烁 + 缓慢流动的波形（明确"在忙，不是卡死"） | 正在思考，请稍等（已等待 N s，可打断） | **打断** / 静音 / 挂断 |
| 正在回答 | 波形按语音韵律起伏 + **当前朗读句字幕**（逐块高亮） | 正在回答（可打断） | **打断** / 静音 / 挂断 |
| 等待确认 | 面板内直接渲染**计划步骤卡片** | 计划已生成，确认后开始执行 | 继续执行 / 说「继续」 / 挂断 |

- **字幕**：`voice_audio` 事件带 `text`，播放队列在每块开始时回调 `onChunkStart`，界面显示"正在朗读的这句"，
  解决"只听到声音、看不到在说什么"；完整答复仍在对话气泡里。
- **打断**（`stopStream()`）：停止播报 + `AbortController` 中止 SSE + 重新同步挂起状态；
  之后可以继续说：
  - 若打断发生在**执行中** → 下一轮开始时后端 `prepare_turn()` 会把卡在 `in_progress` 的任务复位
    （自愈，日志"已复位上一轮被打断的任务 数量=N"），不会假死；
  - 若打断发生在**等待确认处** → 下一句会被 `/chat` 以 1103 拦下，前端**自动改走 `/resume`** 重发这句话，
    用户不用重复说。

> 为什么复位放在"下一轮开始"而不是"打断时"：客户端断开时 Starlette 会取消生成器，`finally` 里的 `await`
> 会被立刻取消（实测复位不生效、无日志）。放到下一轮开始时读一次 checkpoint 顺便清理，既可靠又只多一次状态读取。

## 6. 配置（`config.yaml` 的 `voice` 段）

```yaml
voice:
  enabled: true
  base_url: https://api.siliconflow.cn/v1   # OpenAI 兼容语音接口
  api_key_env: SILICONFLOW_KEY              # Key 的环境变量名（不存明文）
  tts_model: FunAudioLLM/CosyVoice2-0.5B
  tts_voice: FunAudioLLM/CosyVoice2-0.5B:alex
  chunk_max_chars: 60         # 单块上限（越大越少切，但单块更慢）
  chunk_min_chars: 12         # 单块下限（短句并到下一句）
  first_chunk_max_chars: 30   # 首块上限：越小第一声越快
  max_chunks: 20              # 最多合成块数
  timeout: 45                 # 单次 TTS 超时（秒）
```

## 7. 接口

| 接口 | 变化 |
|------|------|
| `POST /sessions/{id}/chat` | 新增请求字段 `voice: bool`；为 true 时答复后追加 `voice_audio` / `voice_end` 事件 |
| `POST /sessions/{id}/resume` | 同上（语音确认/意见走这里） |
| `POST /sessions/{id}/chat/sync` | 支持 `voice`（当前仅影响回答风格，不返回音频） |

语音消息与文字消息同表落库（`messages`），助手消息 `payload.channel = "voice"` 便于区分渠道。

## 8. 隐私与合规

- 麦克风音频**不上传**（识别在浏览器完成），服务端只收到识别后的文本；
- 语音合成只把**答复文本**发给 TTS 服务商；
- 浏览器原生识别是否经过厂商云端取决于浏览器实现（Chrome 走 Google），如不能接受，可换下面的本地识别路线。

## 9. 后续可扩展

1. **跨浏览器识别**：接本地 `faster-whisper` / `whisper.cpp`（服务端推理，音频不出内网），代价是要装依赖（约 100–200MB）与 CPU 推理；
2. **边说边播（流式 TTS）**：现在答复是"整段生成 → 逐句合成"，若把节点答复改成分段流式输出，可以做到"说到第一句就开始播"；
3. **打断（barge-in）**：用户开口即停播当前音频（前端已有停止能力，只差一个门限策略）；
4. **真人电话**：同一套"识别 → agent → 合成"管线可挂到 PSTN 网关（Twilio/阿里云语音等），届时只需新增一个适配层与公网回调地址。
