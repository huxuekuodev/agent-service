# 规划协议方案（计划 = 工具提交 + 契约校验）

> 状态：已实施。影响 `app/agents/plan/`（新增）、`app/agents/dispatch/node.py`、`app/agents/graph/agent.py`。
> 提示词同步：`plan_node_system_prompt`（本地副本 `app/prompts/plan_system_prompt_v2.md`，需推 Langfuse 新版本）。

## 1. 问题：业务契约被绑死在渠道特性上

规划节点要的是「一张可执行的 DAG」。原实现用 LangChain 的结构化输出表达这个契约：

```python
create_agent(model, tools, response_format=PlanOutput)   # ← 曾经的写法
```

`response_format=Schema` 内部走 `ToolStrategy`，而 `ToolStrategy` 的实现是**强制模型调用结构化输出工具**——请求里带 `tool_choice="required"`（`langchain/agents/factory.py::_get_bound_model` 把 `any` 映射成 `required`，且写死、无开关）。

thinking 渠道不允许强制工具调用：

| 请求 | DeepSeek `deepseek-flash` / `deepseek-v4-pro` |
|---|---|
| `tool_choice=required` / 指定函数名 | ❌ 400 `Thinking mode does not support this tool_choice` |
| 同上 + `thinking={"type":"disabled"}` | ✅ 但等于放弃思考能力 |
| `response_format=json_schema` | ❌ 400 `This response_format type is unavailable now` |
| `response_format=json_object` + 工具 | ⚠️ 不稳定：有时把工具调用写成文本（`tool_calls=[]`），agent 循环静默失效 |
| `tool_choice=auto` / 不带 | ✅ 正常 |

结论：**"计划必须是 DAG" 是业务契约，不该由渠道能力决定能不能表达。** 一旦把契约做成渠道特性，换渠道就得在渠道层打补丁，业务节点还要为兼容性长出一堆分支。

## 2. 方案：计划提交是普通工具，契约由代码校验

```
模型 ──submit_plan(args=PlanOutput)──► pydantic 校验（schema.py）
                                          │ 合法
                                          ▼
                                   「提交即终态」中间件：写应答 ToolMessage → 结束本轮
                                          │ 不合法
                                          ▼
                                   工具节点把校验错误回给模型 → 模型自修后重新提交
```

三个部件（都在 `app/agents/plan/`，业务契约不依赖任何渠道特性）：

| 文件 | 职责 |
|---|---|
| `schema.py` | 契约与不变式：`action ∈ {create,update,complete}`、`plan_id` 唯一且字符安全、`deps` 无自依赖/无环、`complete` 时 `tasks` 空且 `answer` 非空、`create` 时 `deps` 只能指向本次任务、`skill_probe` 保留 id 不可占用 |
| `dag.py` | 运行期 DAG 操作：契约 → `SubTask`、**拓扑校验/修复**（依赖必须存在）、技能探测注入、`pick_ready()` 就绪筛选、`<PlanStatus>` 渲染；规划节点与派发节点共用同一份语义 |
| `protocol.py` | `submit_plan` 工具（`args_schema=PlanOutput`）+ `PlanSubmissionMiddleware`（提交即终态） |

节点侧只有一条读取路径：

```python
# app/agents/plan/node.py（不再有 response_format）
agent = create_agent(llm, [*await get_plan_tools(), submit_plan],
                     middleware=[DanglingToolCallMiddleware(), ClarificationMiddleware(), PlanSubmissionMiddleware()],
                     system_prompt=await build_system_prompt(...))
...
for call in msg.tool_calls:                      # 从完整的 AIMessage 读，权威且可校验
    if call["name"] == SUBMIT_TOOL_NAME:
        run.plan_output = parse_submission(call["args"])
```

### 为什么"提交即终态"要单独做中间件

框架内置结构化输出在拿到结果后立刻结束本轮；改成普通工具后，模型提交完还会再补一句"计划已提交"——白付一次 thinking 调用（数秒延迟 + token），transcript 也多出无意义消息。中间件用公开扩展点 `@hook_config(can_jump_to=["end"])` 复刻该语义：写入应答 `ToolMessage`（保证历史不出现悬空 tool call）后跳转 END。

**只拦截完全合法的单独提交**：参数不合法、或与其它工具混用时返回 `None`，交给工具节点按标准流程处理（校验错误回给模型自修 / 正常执行工具）。

## 3. DAG 校验：把"永不执行的任务"挡在落库前

原实现的 `_to_subtask()` 原样接收模型给的拓扑，而派发节点用 `status_map.get(dep) != "completed"` 判就绪。后果很具体：模型把 `deps` 写成不存在的 id（或重复 `plan_id`、自依赖、成环）时，**任务永久阻塞、不报错、用户拿到空结果**。

现在分两层兜住：

1. **schema 层**（不看历史状态就能判断的）：唯一 id、无自依赖、无环、`action` 自洽 —— 由工具参数校验触发，非法即带错误信息回到模型自修；
2. **dag 层**（需要历史状态的）：`validate_topology(plan, known_ids)` 校验依赖指向的任务是否存在（`update` 允许依赖旧计划任务），`repair_topology()` 剔除不存在的依赖并向前端播一条提示。

派发节点改为共用 `pick_ready(plan_tasks)`：就绪判定与 `blocked_message` 只有一处实现。

## 4. 与旧实现对比

| | 旧：`response_format=PlanOutput` | 新：`submit_plan` 工具 |
|---|---|---|
| 请求形态 | 依赖渠道：`tool_choice=required` | 所有渠道一致：普通工具调用（`auto`） |
| thinking 渠道 | ❌ 400（需要渠道层降级补丁） | ✅ 原生可用 |
| 输出解析 | 三路兼容（native / tool-call / JSON 文本兜底） | 一路：工具参数 + pydantic |
| 契约校验 | 仅 pydantic 字段 | 字段 + DAG 不变式 + 拓扑 |
| 校验失败 | 框架内部重试 | 错误文本回给模型自修（可见、可测） |
| 循环收尾 | 框架保证 | 中间件复刻同一语义 |
| 渠道层代码 | 需要兼容补丁 | **零特例** |

## 5. 迁移与回滚

- 提示词：`submit_plan` 是计划的唯一出口，正文不再输出 JSON（`app/prompts/plan_system_prompt_v2.md`，推 Langfuse 后 `plan_node_system_prompt` 版本 +1）。
- 删除：`app/llm/compat.py`、`LLMInstance.supports_forced_tool_choice`、`_extract_json_text/_try_parse_plan/_extract_plan_output`。
- 回滚：恢复 `response_format=PlanOutput` 即可（但 thinking 渠道会重新 400）。
- 回归关注点：模型一次通过率（是否稳定提交合法 DAG）、`skill_probe` 注入与依赖重排是否照旧、审查轮 `action=complete` 的答案质量。
