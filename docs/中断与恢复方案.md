# 人工确认与恢复方案（interrupt / resume）

> 目标：把"执行前让用户看一眼计划、可以提意见"做成一条**可靠**的链路；同时说明为什么
> 恢复必须走独立接口，以及协议长什么样（未来清理确认、澄清追问都复用这一套）。

## 1. 为什么要单独设计：挂起 ≠ 新消息

LangGraph 的 `interrupt(value)` 会把 `value` 冻结进 checkpoint 并让本次运行停下；恢复时必须
用 `Command(resume=answer)` 把答复交回**同一个 `interrupt()` 调用点**。用本仓库的
langgraph 1.2.10 实测（`InMemorySaver` + 一个 `interrupt()` 节点）：

| 调用方式 | 结果 |
|---------|------|
| 首次调用命中 `interrupt()` | 正常挂起：`__interrupt__=[Interrupt(value=…, id=A)]`，`state.next=('node',)` |
| 挂起状态下再发**普通输入** | **不报错、也不消费挂起**：节点带新输入重跑并生成**新的** interrupt，旧的 A 仍挂着 → 用户答复被丢弃、图停在原地 |
| `Command(resume=<答复>)` | 正确恢复：节点拿到答复继续执行，`next=()`、`interrupts=()` |

结论：**不能在 `/chat` 里"兼容"恢复**——它会静默丢答复（HTTP 200、SSE 正常结束，但什么都没发生），
是生产里最难排查的一类错。因此：

- `/chat` 在会话有挂起时**直接拒绝**（业务码 `1103`），让前端改走恢复接口；
- 恢复接口 `POST /sessions/{id}/resume` 只做一件事：把用户答复交给挂起的节点继续执行。

## 2. 协议（节点问什么 / 前端答什么）

节点侧（`app/agents/interrupts.build_ask`，只展示、不强迫选择）：

```json
{
  "type": "plan_review",
  "title": "计划已生成，确认后开始执行",
  "content": "以下是将要执行的步骤：",
  "items": [{ "plan_id": "task1", "name": "查询北京天气", "desc": "…", "skill_id": "query-weather" }],
  "questions": [
    { "id": "review", "question": "需要调整吗？可以直接继续执行，也可以写下你的意见。",
      "options": [], "allow_custom": true, "custom_placeholder": "例如：把北京换成上海" }
  ]
}
```

前端答（与 `ask_user_question` 的 answers 结构对齐，天然支持一次问多个问题）：

```json
{ "interrupt_id": "…", "answers": [{ "id": "review", "selected": [], "custom": "把北京换成上海" }] }
```

语义（由节点解释，协议只搬运）：

| 答复 | 含义 | 节点行为 |
|------|------|---------|
| `answers` 为空 / `custom` 为空 | 照此计划执行 | 标记任务 in_progress，进入执行 |
| `custom` 非空 | 用户提了意见 | 注入一条 HumanMessage 并 `goto="plan_model_node"` 重新规划（重排后**再次**要用户确认） |

兼容：`parse_answer` 同时认旧形态 `{"continue": bool, "suggestion": str}` 及其 JSON 字符串（历史 checkpoint 里的中断值不会被解析炸掉）。

## 3. 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/sessions/{id}/chat` | 新一轮对话。会话有挂起时返回 `1103`（提示改走 `/resume`） |
| POST | `/sessions/{id}/resume` | 恢复挂起的运行（SSE，同一信封 / 同一落库流程） |
| GET | `/sessions/{id}` | 会话详情，带 `pending_interrupt: {interrupt_id, payload, next}`（刷新页面恢复卡片） |
| SSE | `{"type":"interrupt","data":{"interrupt_id":…,"payload":{…}}}` | 运行被挂起时推送，前端据此渲染确认卡片 |

`/resume` 的请求体：`{ "answers": [...], "interrupt_id": "…", "client_msg_id": "…" }`；
错误码：`1103`（有挂起却发新消息）、`1104`（没有挂起却调 resume）、`1105`（卡片过期：interrupt_id 不一致）。

落库：用户的答复按 `role=user`（内容为意见，留空则记「（继续执行）」）、助手后续回复按
`role=assistant, kind=answer/error` 写入 `messages`，历史里能看到"我提了什么意见"。

## 4. 实现要点（易踩的坑）

1. **`Command` 不能被当普通输入处理**：`GraphAgent.astream` 里原来会对输入做
   `payload.setdefault(...)`，`Command` 没有该方法——必须走独立分支原样透传
   （`resume=` 参数 + `_NO_RESUME` 哨兵区分"没传"与"传了 None"）。
2. **只在确实要派发任务时中断**：`step_dispatch_node` 每轮都会被执行（执行完还会回来），
   若无条件 `interrupt()`，用户会在没有新任务时被反复要求确认。现在先算出"本轮可执行任务"，
   有才问。
3. **不展示系统内部任务**：`skill_probe` 这类校验任务是框架注入的，既不展示也不需要批准
   （`approval.show_internal_tasks=false`；若一轮里只有内部任务则完全不中断）。
4. **`updates` 通道要翻译**：`__interrupt__` 藏在 `updates` 里，`AgentService._translate_event`
   把它翻成 `interrupt` 事件，其余状态更新不外发（否则内部消息会上屏）。
5. **合并 reducer 的 PATCH 语义**（本次一并修掉的真 bug）：`merge_plan_tasks` 曾把
   `name/desc/deps` 视为永久不可变，导致"提意见→重排"改了描述却不生效（卡片还显示旧任务）；
   同时空 `result` 会把已完成任务的结果**清空**。现在规则是：
   - 状态字段（`step_statuses/result/blocked_message`）：非"默认值/空值"才覆盖；
   - 定义字段（`name/desc/deps/sort/execution_agent/skill_id`）：**仅当任务仍 `not_started`** 时可覆盖，
     已开始/已完成的任务定义冻结（结果属于旧定义）。

## 5. 配置

```yaml
approval:
  plan_review: true          # 计划生成后中断等待确认（false = 直接执行，自动化/压测用）
  show_internal_tasks: false # 确认卡片是否展示系统内部任务（skill_probe 等）
  allow_feedback: true       # 允许用户只提意见不选选项
```

## 6. 前端

- 事件 `interrupt` → `ConfirmCard`（展示步骤清单 + 意见输入框 + 「继续执行」/「提交意见并重排」）；
- 切会话 / 刷新页面时用 `GET /sessions/{id}` 的 `pending_interrupt` 恢复卡片；
- 卡片提交走 `resumeSession()`（与 `chatStream()` 共用同一套 SSE 读取逻辑）；
- `/chat` 返回 `1103` 时自动刷新卡片而不是报错。

## 7. 验证

- 离线单测：`tests/test_interrupts.py`（协议解析含旧形态兼容、updates 提取、合并语义含冻结与不被清空）；
- 端到端（真实模型 + 真实 E2B 沙箱）：发消息 → 收到 `interrupt`（只含面向用户的任务）→
  挂起时 `/chat` 返回 1103 → `GET` 详情带 `pending_interrupt` → `/resume` 无意见继续执行并落库 →
  无挂起时 `/resume` 返回 1104 → 提意见后重排（卡片变为新计划）→ 旧卡片重复提交返回 1105。
