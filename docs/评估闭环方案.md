# 评估闭环方案（评估 → 归因 → 行动 → 验证）

> 背景：改造前评估只落一条打点（`p0=评估器, p1=指标, p2=得分, p3=passed`），
> 结果是"能看平均分，但没法据此改进"。本方案把它变成**能指挥升级的闭环**。

## 1. 为什么原来的评估"用不起来"

| # | 缺口 | 后果 |
|---|------|------|
| 1 | 打点里**没有身份** | 不知道这条分属于哪次对话、哪个 plan/task、哪个技能 → 无法回到现场 |
| 2 | 打点里**没有版本** | 不知道被评的是哪个 prompt 版本 / 哪个模型 / 哪版代码 → **改动前后无法对比** |
| 3 | 评语只在 Langfuse | 业务侧查不到、不能按会话 join → 报表只有数字，没有"为什么低分" |
| 4 | 没有**低分样本沉淀** | 拿不到"问题 + 计划 + 产出 + 评语"的原文 → 没有改 prompt 的原料 |
| 5 | 没有**离线评测集与基线** | 改完只能靠感觉 → 无法证明"变好了" |
| 6 | 成本策略粗糙 | `sample_rate=1.0`、每轮两个 judge、跑在对话链路里 |

## 2. 闭环设计

```
在线评估（值得评才评 + 异步）
   └─ evaluations（带身份与版本）──┬─→ 监控面板：按 prompt 版本 / 模型 / 技能 / 渠道切片对比
                                   ├─→ bad case 归档（eval_samples，含完整上下文，可回放）
                                   └─→ 用户反馈 👍/👎（最便宜最真实的信号）
                                          ↓
                                    针对性行动：改 prompt / 沉淀 few-shot / 改技能或脚本 / 换模型路由
                                          ↓
                                    离线跑批（evalsets + 基线对比）→ 数据证明有效 → 上线（可回滚）
```

### 2.1 评估记录（`evaluations` 表）

每条指标一行，关键字段：`session_id / message_id / node / evaluator / metric / score / passed / rationale`、
`plan_id / task_id / skill_id`、**`run_model / run_prompt_version / judge_model / git_sha / channel`**、`meta.signals`。

- `run_prompt_version`：plan 节点取 Langfuse prompt 版本（如 `langfuse:v4`）；执行节点缺失时用本地文件内容哈希（`local:ab12cd34`）——
  **改了提示词版本就会变**，这是"改进是否有效"的对比基准；
- `meta.signals`：记录本轮命中了哪些"值得评"信号（replan/澄清/多任务…），便于事后统计"哪种轮次最容易出问题"。

### 2.2 值得评才评（`evaluation_policy`）

| 配置 | 默认 | 说明 |
|------|------|------|
| `mode` | `worth_it` | `worth_it` / `always`（全量）/ `off`（不评） |
| `baseline_sample_rate` | `0.05` | 普通轮次的抽样率 |
| `async_enabled` | `true` | 评估放后台，不占对话延迟 |
| `max_concurrency` | `2` | 后台评估并发上限 |
| `archive_bad_cases` | `true` | 低分样本连同完整上下文归档 |

命中任一信号即评：`replan`（在旧计划上继续）、`failed_task`、`clarify`、`first_turn`、
`user_follow_up`、`many_tasks`（≥3）、`skill_used`。

> 依据：大量"一次拆解就成功"的轮次评分集中在 4–5 分，看不出差异；真正有信号的是出过问题的轮次。

### 2.3 改进原料（`eval_samples`）

- `kind=bad_case`：低于 3 分的指标自动归档，含 `input`（用户问题/历史）、`output`（计划或答复）、
  `context`（全部指标分、评语、模型、prompt 版本、代码版本、技能、信号）——**可直接拿去改 prompt / 改技能**；
- `kind=feedback`：用户 👍/👎（对话气泡上的按钮），可选原因；`score` 记 5/1，便于和 LLM judge 做一致性对比。

### 2.4 查看与对比

| 接口 | 用途 |
|------|------|
| `GET /monitor/evaluations/summary?dimension=&metric=` | 按 **prompt 版本 / 模型 / 技能 / 节点 / 渠道 / 代码版本** 聚合：均值、通过率、样本数 |
| `GET /monitor/evaluations/trend?metric=&dimension=` | 按天趋势（改动上线后是否变好） |
| `GET /monitor/evaluations/bad-cases` | 低分案例列表（含上下文） |
| `GET /monitor/evaluations/feedback` | 用户反馈列表 |
| `POST /sessions/{id}/feedback` | 提交 👍/👎 |

监控页「🎯 评估闭环」面板：切片维度下拉 + 指标过滤 + 汇总表 + 低分案例 + 用户反馈。

### 2.5 离线跑批（验证环节）

```bash
# 1) 跑一轮并落报告（自动与上次同评测集报告对比）
uv run python scripts/run_eval.py --label before-prompt-v5

# 2) 改 prompt / 换模型 / 改技能后
uv run python scripts/run_eval.py --label after-prompt-v5

# 3) 报告在 reports/eval-*.json，含每指标 基线 vs 候选 的变化（🟢/🔴/⚪）
```

- 评测集：`evalsets/core.yaml`（问题 + 标签 + 期望要点：`should_clarify` / `min_tasks` / `max_tasks` / `must_cover`）；
- 跑批期间强制 `mode=always` + `async_enabled=false`，保证每条用例都被评估；
- 通过 `app.evaluation.register_sink()` 直接收集评估记录（不依赖数据库），每条用例独立 thread；
- 支持 `--smoke`（2 条冒烟）/ `--limit N` / `--baseline 指定报告`。

## 3. 实施状态

**已完成**
- `app/evaluation/`：`context`（RunMeta 身份：会话/消息/任务/技能/模型/prompt 版本/代码版本）、
  `policy`（值得评才评）、`store`（`evaluations`/`eval_samples` 读写 + 聚合查询）、
  `recorder`（落库 + 打点 + 低分归档 + 后台异步 + 进程内 sink）；
- 业务库：`evaluations` + `eval_samples`（`deploy/sql/business_schema.sql`，迁移版本 `20260913_002_evaluations`）；
- 打点补齐：`p4` 会话、`p5` 计划/任务、`p6` 被评 prompt 版本、`p7` 被评模型；
- 节点接线：plan 节点写 Langfuse prompt 版本 + 运行信号；执行节点写任务/技能/模型 + 提示词版本标识；
- 两个评估器改走策略门 + 统一记录器（默认后台异步，不拖慢对话）；
- 查询接口 + 监控页「评估闭环」面板 + 对话气泡 👍/👎；
- `evalsets/core.yaml`（8 条）+ `scripts/run_eval.py`（跑批 + 基线对比 + 报告）。

**跑批实测发现的两个真问题（已修 / 待跟进）**
1. ✅ **指标适用性**：没有工具调用的纯回答任务也会被评 `path_efficiency` 并打低分，污染均值 →
   已加 `GeneralEvaluator.is_metric_applicable`：无工具活动时不评路径效率；
2. ⚠️ **judge 单次评分噪声不小**：同一条用例两次跑出 `answer_cleanness` 1 分 vs 5 分。
   因此：评测集样本量要够（建议 ≥30 条）、关键指标建议同 case 跑 N 次取均值，或叠加规则化校验
   （可复现的硬指标优先，LLM judge 用于软指标）。

## 4. 后续（P2，未做）

- 失败模式聚类（把 rationale 归类到"目标不清/任务过大/依赖缺失/工具选错"等预设模式）→ 自动生成 prompt 补丁候选（diff + 理由，人工审批后推送 Langfuse）；
- 高分轨迹自动沉淀为 few-shot 示例池；
- 技能改进建议（按 `skill_id` 聚合低分 → 定位 STKILL.md / reference / 脚本参数）；
- 在线 A/B（按 session 哈希稳定分流两个 prompt 版本）；
- CI 门禁：`make eval` 低于基线阈值即失败，发布前必须绿。
